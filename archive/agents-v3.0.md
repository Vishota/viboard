# Правила для агентов — viboard (файловая доска) · v3.0

Версия: 3.0 · 2026-11-23 · Заменяет: v2.6 (снапшот archive/agents-v2.6.md — правила и протокол доски одним файлом). Ключевые слова: «обязан» / «следует» / «может» (= MUST / SHOULD / MAY). Обязателен к прочтению каждой сессией перед работой.

Здесь — как работать в этом репозитории. Протокол доски (как агенту работать с доской) — в `protocol/`: это единственный источник нормативной истины по протоколу, он ставится в каждую доску и читается по ролям (UD-16, UD-21, UD-25).

## 1. Роли файлов и приоритет

| Файл/каталог | Роль | Статус |
|---|---|---|
| `agents.md` | Этот файл: процесс в репозитории — полномочия, протокол сессии, инженерный контур, коммиты | всегда актуален |
| `protocol/` | Канон протокола доски: `AGENTS.md` (ядро — читается целиком), `manager.md`, `reviewer.md`, `tokens.md`, `security.md` (по необходимости); `shell.md` в доске собирается из кода. Попадает в доску через `viboard init` | всегда актуален |
| `decisions.md` | Журнал решений владельца: дословно, UD-N, не перенумеровывается | всегда актуален |
| `current/` | Открытые вопросы (`open-questions.md`), доказательства прогонов (`qa/`) | актуально |
| `archive/` | Снапшоты прошлых версий правил. Только чтение, нормативной силы нет | история |
| `src/` `ui/` `test/` | Код пакета: ядро, CLI, сервер (TypeScript); интерфейс (Vue 3); тесты | — |
| `board/` | Живая доска владельца — данные, не документация; регулируется `protocol/` | — |

Приоритет: agents > decisions > protocol > current > archive. Противоречие архива этому файлу гасится этим файлом. Один факт — в одном месте: форматы файлов доски описаны только в `protocol/`, команды — только в `viboard help`.

## 2. Цель

**Цель (UD-18, UD-19, UD-20).** Публичный продукт: доска задач, в которой владелец работает как в Trello — через интерфейс, — а ИИ-агент видит те же задачи как обычные файлы (`ls` и `cat`) и тратит минимум токенов. Два сценария: владелец назначает менеджера-агента, который разбирает доску и раздаёт задачи сессиям; или сам пишет агенту «возьми вот эту». Публикация — ради узнаваемости vishota.com и личного бренда владельца; аудитория — в том числе вайбкодеры без Node и Docker.

**НЕ-цели:** не трекер с базой данных и сервером состояния; не среда запуска агентов (как запустить сессию — решает среда); не мессенджер; не замена git.

## 3. Полномочия сессии

| Уровень | Действие | Критерий |
|---|---|---|
| Сам, в текст работы | win-win правки, вытекающие из принятых решений и аксиом | очевидное улучшение, ничего не ломает, семантику протокола не меняет |
| Сам + доклад в следующем сообщении | низкая цена + явный выигрыш; помечать в decisions «принято по правилу автономии» | оба условия явные |
| Только владелец | семантика протокола, новые сущности, имя и публикация, необратимое | пакетом вопросов с рекомендацией |

Мандат упрощения (UD-22): при каждом изменении искать, что удалить или слить; усложнение — только через вопрос. Замалчивание сомнений запрещено: несогласие — явно и отдельно от исполнения.

Соответствие представления данным — норма уровня агента: подписи интерфейса равны именам файловой системы и протокола (`backlog`, `todo`, `lock-<тег>`), соблюдаются без разрешений; расхождение — только с явной причиной и решением владельца (UD-11, UD-13).

## 4. Протокол сессии

1. Решения владельца — немедленно в `decisions.md`, дословно, с датой; применение — после фиксации.
2. Вопросы владельцу — обычным текстом (не интерактивные опросы): самодостаточные, с вариантами, последствиями и рекомендацией; пакетом. Копия пакета — в `current/open-questions.md`.
3. Промежуточные результаты и формулировки из чата в этот же сеанс копируются в файлы: сжатие контекста не должно иметь возможности их убить.
4. Процессуальные указания владельца («делай так отныне») → в этот файл со ссылкой на UD-N; продуктовые → в `decisions.md`.
5. Продуктовые и интерфейсные изменения — обязательный живой прогон в браузере (реальные клики и ввод) со скриншотами в `current/qa/<дата>-<тема>/` до передачи владельцу: «код написал» ≠ «сделал» (UD-10). Что не удалось воспроизвести автоматизацией (например, жест перетаскивания), называется прямо.
6. Код сдаётся только с зелёными `npm run check` и `npm run build` (UD-25).
7. Коммиты — по поручению владельца. Правила, протокол и код — отдельно от данных доски; сообщение — биография со ссылками на UD-*/N*. Нормативное изменение этого файла или `protocol/` = новая версия, прежняя — снапшотом в `archive/`.

## 5. Инженерный контур (UD-25)

- TypeScript strict (`noUncheckedIndexedAccess`), без зависимостей в рантайме: ядро и сервер — только встроенные модули Node; интерфейс — Vue 3 + Vite, собирается в статику.
- Проверки: ESLint с типизированными правилами, Prettier, `tsc` + `vue-tsc`, Vitest (узел — без DOM, интерфейс — happy-dom). `npm run check` прогоняет всё; CI повторяет на трёх ОС и двух версиях Node.
- Тестом закрепляется каждая операция ядра, каждое правило защиты сервера и каждый найденный вживую дефект интерфейса.
- `protocol/` меняется только как источник: в доску файлы попадают через `viboard init --update-protocol` рукой владельца — сессия не переписывает протокол в чужой доске.
- Форматы файлов доски (имена, frontmatter, записи) рождаются только в `src/core/names.ts` и `src/core/frontmatter.ts`; второе место с той же логикой не заводится.

## 6. Честные границы

1. Одна машина, один владелец; распределённые сценарии вне периметра.
2. Лок — сигнал для честных сессий, не защита от злонамеренных. Возраст лока ничем не продлевается — в этом смысл порога 24 ч.
3. Сессия не знает времени: имена записей — только через CLI или команды из `protocol/shell.md`.
4. Идентичность — тег сессии; долговременной атрибуции между сессиями нет (локи и записи — единственный след).
5. Cookie браузера общие для всех портов хоста: доступ к доске защищает проверка `Origin`, а не cookie (`protocol/security.md`).
