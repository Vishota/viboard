# Правила для агентов — tasks (файловая доска) · v2.2

Версия: 2.2 · 2026-11-20 · Заменяет: v2.1 (снапшот archive/agents-v2.1.md; v2.1 — лицензия UD-8). Ключевые слова: «обязан» / «следует» / «может» (= MUST / SHOULD / MAY). Обязателен к прочтению каждой сессией перед работой с доской. Единственный источник нормативной истины по протоколу (UD-6).

## 1. Роли файлов и приоритет

| Файл/каталог | Роль | Статус |
|---|---|---|
| `agents.md` | Настоящие правила: протокол доски (структура, карточки, локи, логи, вопросы, роли, vistamp) + процесс | всегда актуален |
| `decisions.md` | Журнал решений владельца: дословно, UD-N, не перенумеровывается | всегда актуален |
| `current/` | Разборы, планы, отчёты, open-questions | актуально |
| `archive/` | Снапшоты прошлых версий правил. Только чтение, нормативной силы нет | история |
| `board/` | Живая доска — **данные, не документация**; регулируется этим файлом | всегда актуальна |
| `tools/` | vistamp (§13) и будущие инструменты | — |

Приоритет: agents > decisions > current > archive. Противоречие архива этому файлу гасится этим файлом.

## 2. Аксиоматика (норма, противоречащая аксиоме, недействительна)

- **А1 (ФС = правда, N1).** Единственный источник правды о задачах — файловая система доски. UI, сводки, дайджесты — проекции без собственного состояния. Один факт фиксируется в одном месте.
- **А2 (присутствие = сигнал).** Существование файла/папки — событие: позиция карточки = статус; `.lock-<session>` = «занято, держатель такой-то»; отсутствие `answer.md` = вопрос открыт; запись в проектном логе = условие done.
- **А3 (человек ставит).** Тело карточки и `answer.md` пишет только владелец. Менеджер не редактирует тело — непонятная карточка возвращается вопросом, не дописыванием.
- **А4 (детерминистика в CLI).** Время, имена записей, номера id, ре-резолв путей — только через vistamp. Сессия не «знает» время и не набирает имена вручную.
- **А5 (агент-агностичность, UD-4).** Протокол исполняется любой средой, умеющей файлы и команды; планировщики запусков — вне системы.
- **А6 (экономия токенов).** Ленивое чтение: `ls` перед `read`, указатели вместо пересказа, точечное чтение. Дизайн прощает наивное поведение агента.
- **А7 (конвенции вместо замков).** Проверки дают видимость, не принуждение. Единственное железное правило (цена ошибки асимметрична): карточку в doing/ трогает только держатель её лока.
- **А8 (идентичность = сессия, UD-5).** Агент = сессия. Реестров агентов, имён-персон, capabilities нет; «кто держит» восстанавливается по имени лока.

## 3. Идентичность и клэйм (UD-5)

1. Сессия подтверждает взятие карточки локом `mkdir .lock-<session>` внутри неё — атомарно; не создался ⇒ занято. Внутри лока ничего нет. Поле `assignee` упразднено: лок — единственная фиксация факта взятия.
2. Менеджер может напрямую указать запущенной сессии карточку (транспорт среды) — но фиксация взятия в любом случае лок.
3. WIP (глобальный дефолт): одна сессия держит не более **2** карточек в doing/; меняется решением владельца (UD).
4. Heartbeat нет (N5): возраст лока = возраст его mtime; лок старше 24ч ⇒ карточку можно перехватить (запись в карточный лог обязательна). Уходя из doing/, держатель снимает свой лок.

## 4. Полномочия сессии (градуированная автономия)

| Уровень | Действие | Критерий |
|---|---|---|
| Сам, в текст работы | win-win правки, вытекающие из принятых решений/аксиом | очевидное улучшение, ничего не ломает, семантику протокола не меняет |
| Сам + доклад в следующем сообщении | низкая цена + явный выигрыш; помечать в decisions «принято по правилу автономии» | оба условия явные |
| Только владелец | семантика протокола, новые сущности, необратимое | пакетом вопросов с рекомендацией |

Мандат упрощения: при каждом изменении правил искать упрощения (удаление сущностей/полей/правил); усложнение — только через вопрос. Замалчивание сомнений запрещено: несогласие — явно, отдельно от исполнения.

## 5. Протокол сессии

1. Решения владельца — немедленно в `decisions.md`, дословно, с датой; применение — после фиксации.
2. Вопросы владельцу — обычным текстом (не интерактивные опросы), самодостаточные, с вариантами, последствиями и рекомендацией; копятся и отдаются пакетом. Асинхронные — механизм §10.
3. Промежуточные результаты и формулировки из чата копируются в файлы той же сессией — сжатие контекста не должно иметь возможности их убить.
4. Процессуальные указания владельца → в этот файл со ссылкой на UD-N; продуктовые → в decisions.
5. Коммиты: доску коммитит только менеджер на проходе (§12.10, N8); изменения правил/инструментов — отдельно от данных доски, сообщение-биография со ссылками UD-*/N*. Нормативное изменение этого файла = новая версия, снапшот предыдущей в archive/.

## 6. Структура доски

```
board/
  backlog/  todo/  doing/  blocked/  review/  done/   # колонки = статусы (§8)
  questions/                                          # вопросы владельцу (§10)
  log/                                                # проектный лог (§9)
  projects.yml                                        # реестр проектов: id → name, path (§13.3)
  .lock-manager-<session>/                            # менеджер-лок на время прохода (§12)
```

Имена карточек уникальны сквозной нумерацией NNN по всей доске; проект карточки — поле `project` во frontmatter (UD-1). Слаг — латиница строчными, цифры, дефисы; кириллица — в телах.

## 7. Карточка

Карточка — всегда папка:

```
board/<column>/<NNN-slug>/
  README.md        # входная точка: frontmatter + тело-постановка
  log/             # карточный лог: массив записей (§9)
  assets/          # вложения (может отсутствовать)
  .lock-<session>/ # лок (§3); в git не попадает
```

README.md:
- **frontmatter** (меняется владельцем/менеджером; сессии не пишут в frontmatter): `id`, `project`, `title`, `priority` (low|normal|high), `depends_on` (список id), `dod` (чеклист приёмки — строки), `created`.
- **тело-постановка**: что и зачем. Пишет только владелец (А3); сессия и менеджер не меняют никогда; уточнения — в карточный лог или вопрос §10.

Путь карточки не кэшируется: ре-резолв по id через `vistamp find` (N6). Шаблон — templates/card-README.md.

## 8. Статусы и переходы

| Переход | Кто двигает | Условие |
|---|---|---|
| backlog → todo | владелец | постановка готова |
| todo → doing | сессия (самозахват §3) | лока нет; WIP соблюдён |
| doing → blocked | держатель | открылся вопрос §10 или зависимость |
| blocked → doing/todo | держатель или менеджер | answer.md появился / зависимость снята |
| doing → review | держатель | DoD отмечен (запись `type: review`), запись проектного лога написана, лок снят |
| review → done | проверяющий | вердикт pass (UD-2); запись проектного лога есть |
| review → doing | проверяющий | вердикт fail + находка в карточном логе |
| любая → backlog | владелец | отказ/переделка постановки |

Значимые события фиксируются записью в карточный лог: клэйм, вопрос, решение, блок, DoD/вердикт, done. Обычные mv записи не требуют — история видна в git (после прохода менеджера) и в записях. Записи иммутабельны: исправление — новая запись со ссылкой на старую.

## 9. Логи (один механизм, два места)

Запись — файл, созданный через vistamp §13: frontmatter (`type`, `card`, `session`) + 1–3 строки сути + указатель на первоисточник. Пересказ и «см. выше» запрещены — запись самодостаточна (А6). Имена сортируются лексикографически (N10).

- **Карточный лог** `card/log/` — «как это происходило»: попытки, тупики, решения, вердикты. Типы: `note` (клэйм, мелочь), `decision`, `question`, `blocked`, `review` (DoD-отметка или вердикт), `done`.
- **Проектный лог** `board/log/` — «что произошло» в терминах задач: типы `done`, `decision`, `note`. Запись при закрытии карточки обязательна — это условие перевода в done/ (§8); в записи — ссылка на карточку.

Ленивая детализация: новый агент читает листинг `board/log/` и только релевантные записи/карточки.

## 10. Вопросы владельцу

```
board/questions/<stamp>-<session>-<card>-q/
  README.md    # frontmatter (from, card, priority, created) + суть + варианты с последствиями + рекомендация
  assets/      # если без вложения не понять
  answer.md    # отсутствует = вопрос открыт (А2)
```

1. Сессия упёрлась → создала вопрос (vistamp), карточку уволокла в blocked/, запись в карточный лог. Сессия может умереть — вопрос переживёт.
2. Варианты — с полными формулировками и последствиями, с рекомендацией; вопрос самодостаточен.
3. `answer.md` создают: владелец, UI или живая сессия (фиксирует дословно ответ из чата). Сессии `answer.md` не редактируют; непонятный ответ — новый вопрос со ссылкой на старый.
4. Мимолётное уточнение в живой сессии — в чате, пакетом; но решение, влияющее на карточку, обязано материализоваться: `answer.md` или запись `type: decision` в карточный лог (N9).
5. После появления `answer.md` карточку развязывает менеджер на проходе или сам вопросивший.

## 11. Роли

| Роль | Что делает | Не делает |
|---|---|---|
| Владелец | постановки (тела карточек), приоритеты, ответы, семантические и продуктовые решения (UD: этого репо — для системы; прикладного проекта — его decisions.md) | — |
| Менеджер | поддерживает todo/ приоритизированным; валидация §12; коммит доски; развязка blocked/; вопросы needs-clarification; может указать запущенной сессии карточку | не редактирует тела и answer.md; не двигает залоченное; не пишет постановки (А3) |
| Сессия-исполнитель | самозахват §3, работа, карточный лог, DoD, запись проектного лога, mv в review/, снятие лока | не переписывает постановку; не трогает чужие doing/-карточки |
| Проверяющий | верификация по постановке + DoD + диффам; вердикт `type: review` (pass/fail + находки в формате method §7); mv в done/ или возврат | не исполнитель этой карточки; не переписывает постановку |

Менеджер и проверяющий — роли, которые берёт любая сессия по поручению владельца (А5, UD-4). Менеджеру следуют работать на дешёвой модели: его суждение нужно только в серых зонах роутинга.

## 12. Проход менеджера (чек-лист валидатора)

Перед проходом: `mkdir board/.lock-manager-<session>` (один проход одновременно); после — снять.

1. **blocked/**: появился `answer.md`? → развязать (mv в todo/ или doing/).
2. **doing/**: лока нет? → возврат в todo/ + запись в лог. Лок старше 24ч → перехват §3.4 или вопрос владельцу.
3. **WIP**: у сессии (по именам локов) больше 2 карточек в doing/ → излишек вернуть в todo/ + запись в лог.
4. **depends_on**: ссылки существуют; зависимости не в backlog/.
5. **review/**: карточка без вердикта → поручить проверяющего (доклад владельцу пакетом).
6. **done/**: записи проектного лога нет? → возврат в doing/ (дописывать за исполнителя нельзя).
7. **questions/**: открытые дольше порога → самодостаточный пакет владельцу с рекомендацией.
8. **Имена записей логов** соответствуют формату vistamp; мусор — переименовать через vistamp и записать в лог.
9. Двигать только незалоченное.
10. **git commit доски** — коммит-биография: счётчики переходов, ссылки UD-*/N* (N8, method §9). После — снять менеджер-лок.

## 13. Инструменты

### 13.1. vistamp (спека)

Node stdlib, без зависимостей. Запуск: `node <repo>/tools/vistamp/vistamp.mjs <verb> …`.

- `stamp --session <id> --card <NNN-slug|-> --kind <тип> [--dir <каталог>]` → печатает токен `YYYY-MM-DDTHHMMSSZ-<session>-<card>-<kind>` (UTC, секунды). Файл записи = токен + `.md`; каталог вопроса = токен. Коллизия — следующий свободный момент в секундах (N10). Типы: `note, decision, question, blocked, review, done, q`.
- `id --slug <slug> [--board <путь>]` → `<NNN-slug>`: NNN = max по всем колонкам + 1 (pad до 3). Слаг `^[a-z0-9-]+$`.
- `find <id|фрагмент> [--board <путь>]` → абсолютные пути карточек, чьё имя содержит фрагмент — ре-резолв после mv (N6).

Публикация vistamp в npm возможна (UD-7); лицензия — GPL-3.0-only (UD-8, файл tools/vistamp/LICENSE); поле `repository` не ставится, пока репозиторий private (UD-8).

### 13.2. board-ui (спека)

Stateless-проекция доски (А1), localhost без аутентификации. Запуск: `node <repo>/tools/board-ui/server.mjs [--board <путь>] [--port 8777]`. Умеет только: показывать колонки, карточки, вопросы; **создавать карточку от имени владельца** (текст постановки вводит владелец — А3 соблюдён: UI — его рука; создание только в backlog/ и todo/); **писать `answer.md`** (только если его ещё нет). Не умеет: двигать карточки (v0 — движение делают держатели/менеджер), редактировать тела и `answer.md`, хранить своё состояние. Обновление — опрос раз в ~2.5с.

### 13.3. projects.yml (реестр проектов центральной доски)

`board/projects.yml`: id проекта → `name` (человекочитаемое имя) и `path` (локальный рабочий каталог, где исполняется работа). По нему UI показывает проект, исполнитель находит, где работать. Карточка ссылается на проект полем `project` (UD-1).

## 14. Экономия токенов (нормативная)

1. `ls` перед `read`: статус и таймлайн — листингом колонок и `board/log/`, без чтения содержимого.
2. Карточка читается точечно: README + нужные записи лога.
3. Записи 1–3 строки + указатель; запись самодостаточна.
4. Промежуточная отчётность без потребителя не пишется; состояние — не append-only (история = git + записи логов).

## 15. Честные границы

1. Одна машина, один пользователь; распределённые сценарии вне периметра.
2. Git-история доски гранулярна до прохода менеджера (N8); durability — ФС и записи логов.
3. Лок — сигнал для честных сессий, не защита от злонамеренных (А7).
4. Возраст лока ничем не продлевается — это и есть смысл порога 24ч (N5).
5. Знание текущего времени у сессии отсутствует: время — только через vistamp (А4).
6. Планирование запусков менеджера/сессий вне системы (UD-4); крон среды может дёргать сессии — протоколу безразлично.
7. Архивация done/ и project-log по месяцам — v2 (N13).
8. Идентичность — только сессия: долговременной атрибуции «кто это сделал» между сессиями нет (локи и записи логов — единственный след).
