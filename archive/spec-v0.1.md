## 0. Сводка и гарантии

Доска — файловая система задач для совместной работы владельца и ИИ-агентов, агент-агностичная (А5, UD-4) и спроектированная под экономию токенов (А6). Состояние выражено только файловой системой; каждый файл/папка является сигналом своего существования. UI, сводки, дайджесты — одноразовые проекции без собственного состояния.

### 0.1. Гарантия совместимости (нормативная)

Потребители (UI, скрипты, агенты) могут полагаться на: состав колонок §3, формат имени карточки §4, поля frontmatter `id`/`title`/`project` §4, протокол вопроса §8, синтаксис vistamp §11. Изменение всего этого — только мажорной версией и явным решением владельца.

## 1. Глоссарий (нормативный; одному механизму — одно имя)

| Термин | Идентификатор | Определение |
|---|---|---|
| Доска | board | Каталог `board/` этого репозитория — единственный источник правды о задачах |
| Колонка | column | Подкаталог доски = статус карточки: backlog, todo, doing, blocked, review, done |
| Карточка | card | Папка `<NNN-slug>/` в колонке; единица работы |
| Клэйм | claim | Факт взятия карточки в работу; фиксируется созданием лока |
| Лок | lock | Папка `.lock-<session>` внутри карточки; атомарный сигнал «занято, держатель такой-то» |
| Карточный лог | card-log | `log/` внутри карточки: массив файлов-записей §7 |
| Проектный лог | project-log | `board/log/`: массив файлов-записей о проекте в целом §7 |
| Вопрос | question | Папка в `board/questions/` — запрос владельцу §8 |
| Менеджер | manager | Роль: диспетчеризация + валидация §9–§10; не постановщик |
| Проверяющий | reviewer | Роль: верификация карточки в review/ (UD-2); не исполнитель |
| Проход менеджера | pass | Один цикл валидации §10; сериализуется менеджер-локом |
| vistamp | vistamp | CLI детерминистики: время, имена, id, ре-резолв §11 |
| Запись | entry | Файл лога: frontmatter + 1–3 строки + указатель |

## 2. Аксиоматика

- **А1 (ФС = правда).** Единственный источник правды — файловая система доски. Всё прочее (UI, сводки) — проекции без собственного состояния. Норма, вводящая второй источник правды о том же факте, недействительна (N1).
- **А2 (присутствие = сигнал).** Существование файла/папки — событие: позиция карточки = статус; `.lock-<session>` = клэйм; отсутствие `answer.md` = вопрос открыт; запись в проектном логе = условие done.
- **А3 (человек ставит, LLM не пишет постановку).** Тело карточки и `answer.md` пишет только владелец. Менеджер не редактирует тело — непонятная карточка возвращается вопросом, не дописыванием.
- **А4 (детерминистика в CLI).** Всё детерминистичное (текущее время, имена записей, номера id, ре-резолв путей) — через vistamp §11. LLM не «знает» время и не набирает имена вручную.
- **А5 (агент-агностичность, UD-4).** Протокол исполняется любым агентом, умеющим читать/писать файлы и запускать команды. Ядро не зависит от конкретной агентной среды; планирование запусков (кроны сред) — вне системы.
- **А6 (экономия токенов).** Ленивое чтение: `ls` перед `read`, указатели вместо пересказа, записи короткие, чтение точечное. Дизайн выбирает формат, прощающий наивное поведение агента.
- **А7 (конвенции вместо замков; асимметрия цены).** Проверки не принуждают, а дают видимость. Единственное железное правило, где цена ошибки асимметрична: карточку в doing/ трогает только держатель её лока (конкурентные правки — потеря работы; дубль работы — дёшево).

## 3. Структура доски

```
board/
  backlog/  todo/  doing/  blocked/  review/  done/   # колонки (§5)
  questions/                                          # вопросы владельцу (§8)
  log/                                                # проектный лог (§7)
  agents/                                             # реестр: agents/<имя>.md (capabilities, wip)
  .lock-manager-<session>/                            # менеджер-лок на время прохода (§10)
```

Имена карточек уникальны сквозной нумерацией NNN по всей доске (независимо от проекта). Проект карточки — поле `project` во frontmatter (UD-1). Слаг — латиница строчными, цифры, дефисы; кириллица — в телах.

## 4. Карточка

Карточка — всегда папка (унифицированный примитив «сущность = папка»):

```
board/<column>/<NNN-slug>/
  README.md        # входная точка: frontmatter + тело-постановка
  log/             # карточный лог: массив записей §7
  assets/          # вложения (может отсутствовать)
  .lock-<session>/ # лок (§6); в git не попадает
```

README.md:
- **frontmatter** (меняется менеджером/владельцем, N7): `id`, `project`, `title`, `priority` (low|normal|high), `assignee` (ставит менеджер при диспетчеризации или агент при клэйме), `depends_on` (список id), `dod` (чеклист приёмки — строки), `created`.
- **тело-постановка**: что и зачем. Пишет только владелец (А3); агент и менеджер не меняют никогда; уточнения — в карточный лог или вопрос §8.

Путь карточки не кэшируется: ре-резолв по id через `vistamp find` (N6). Шаблон — [templates/card-README.md](templates/card-README.md).

## 5. Статусы и переходы

| Колонка | Смысл | Переход | Кто двигает | Условие |
|---|---|---|---|---|
| backlog/ | черновики, не готово к работе | → todo | владелец | постановка готова |
| todo/ | готова к диспетчеризации | → doing | менеджер (assignee) или агент (самозахват §6) | WIP-лимит соблюдён |
| doing/ | в работе | → blocked | держатель | открылся вопрос §8 или зависимость |
| blocked/ | ждёт внешнего | → doing/todo | держатель или менеджер | answer.md появился / зависимость снята |
| doing/ | в работе | → review | держатель | DoD отмечен (запись `type: review`) и запись проектного лога написана; лок снят |
| review/ | на верификации | → done | проверяющий | вердикт pass (UD-2); запись проектного лога есть |
| review/ | на верификации | → doing | проверяющий | вердикт fail + находка в карточном логе |
| любая | — | → backlog | владелец | отказ/переделка постановки |

Значимые события фиксируются записью в карточный лог: клэйм, вопрос, решение, блок, DoD/вердикт, done. Обычные mv записи не требуют — история видна в git (после прохода менеджера, N8) и в самих записях. Записи иммутабельны: исправление — новая запись со ссылкой на старую.

## 6. Клэйм и лок

1. Клэйм = `mkdir .lock-<session>` внутри карточки — атомарен; не создался ⇒ занято, имя папки показывает держателя. Внутри лока ничего нет.
2. Гибрид UD-3: менеджер назначает `assignee` и двигает todo→doing; агент подтверждает клэйм при старте. Самозахват из todo/ разрешён: агент убеждается в отсутствии assignee/лока, создаёт лок, двигает в doing/, ставит assignee, пишет запись (клэйм) в карточный лог.
3. Агент перед самозахватом проверяет свой WIP-лимит (`board/agents/<имя>.md`).
4. Heartbeat нет (N5): возраст лока = возраст его mtime. Лок старше 24ч ⇒ карточку можно перехватить: запись в карточный лог обязательна.
5. Уходя из doing/ (в review/ или blocked/), держатель снимает свой лок.
6. А7: карточку в doing/ трогает только держатель лока. Менеджер залоченную карточку не двигает.

## 7. Логи (один механизм, два места)

Запись — файл, созданный через vistamp §11: frontmatter (`type`, `card`, `agent`) + 1–3 строки сути + указатель на первоисточник. Пересказ запрещён — только указатель (А6). Имя записи сортируется лексикографически (N10).

- **Карточный лог** `card/log/` — «как это происходило»: попытки, тупики, решения, вердикты. Типы: `note` (клэйм, мелочь), `decision`, `question`, `blocked`, `review` (DoD-отметка или вердикт проверяющего), `done`.
- **Проектный лог** `board/log/` — «что произошло» в терминах задач: типы `done`, `decision`, `note`. Пишется при закрытии карточки (условие перевода в done/, §5); в записи — ссылка на карточку `board/<column>/<NNN-slug>/`.

Ленивая детализация: новый агент читает листинг `board/log/` и только релевантные записи/карточки (А6).

## 8. Вопросы владельцу

```
board/questions/<stamp>-<agent>-<card>-q/
  README.md    # frontmatter (from, card, priority, created) + суть + варианты с последствиями + рекомендация
  assets/      # если без вложения не понять
  answer.md    # отсутствует = вопрос открыт (А2)
```

1. Агент упёрся → создал вопрос (vistamp), карточку уволок в blocked/, запись в карточный лог. Сессия может умереть — вопрос переживёт.
2. Варианты — с полными формулировками и последствиями, с рекомендацией (method §4); вопрос самодостаточен.
3. `answer.md` создают: владелец, UI (дословный ответ) или живая сессия (фиксирует дословно ответ из чата). Агенты `answer.md` не редактируют; непонятный ответ — новый вопрос со ссылкой на старый.
4. Мимолётное уточнение в живой сессии — в чате, пакетом (method §4); но решение, влияющее на карточку, обязано материализоваться: `answer.md` или запись `type: decision` в карточный лог. Иначе два источника правды (N9).
5. После появления `answer.md` карточку развязывает менеджер на проходе или сам вопросивший.

## 9. Роли

| Роль | Что делает | Не делает |
|---|---|---|
| Владелец | постановки (тело карточек), приоритеты, ответы, семантические и продуктовые решения (UD-журнал: этого репо — для системы; прикладного проекта — его decisions.md) | — |
| Менеджер | диспетчеризация (assignee, todo→doing), валидация §10, коммит доски, развязка blocked/, вопросы needs-clarification | не редактирует тела карточек и answer.md; не двигает залоченное; не пишет постановки (А3) |
| Агент-исполнитель | клэйм §6, работа, карточный лог, DoD, запись проектного лога, mv в review/, снятие лока | не переписывает постановку; не трогает чужие doing/-карточки |
| Проверяющий | верификация по постановке + DoD + диффам; вердикт `type: review` (pass/fail + находки в формате method §7); mv в done/ или возврат | не исполнитель этой карточки; не переписывает постановку |

Менеджер и проверяющий — роли, которые берёт любая агентная сессия по поручению владельца (А5, UD-4). Менеджеру следуют работать на дешёвой модели: его суждение нужно только в серых зонах роутинга (method §8.3).

## 10. Проход менеджера (чек-лист валидатора)

Перед проходом: `mkdir board/.lock-manager-<session>` (один проход одновременно); после — снять.

1. **blocked/**: у каждого вопроса появился `answer.md`? → развязать (mv в todo/ или doing/ по обстоятельствам).
2. **doing/**: assignee и лок есть? Нет — возврат в todo/ + запись в лог. Лок старше 24ч — перехват по §6.4 или вопрос владельцу.
3. **WIP**: у каждого агента число карточек в doing/ ≤ `wip` из `board/agents/<имя>.md`.
4. **depends_on**: ссылки существуют; зависимости не в backlog/.
5. **review/**: карточки без вердикта — поручить проверяющего (доклад владельцу пакетом).
6. **done/**: запись в проектном логе есть? Нет — возврат в doing/ (дописывать за исполнителя нельзя).
7. **questions/**: открытые дольше порога — доклад владельцу пакетом, самодостаточный, с рекомендацией (method §4).
8. **Имена записей логов** соответствуют формату vistamp; мусор — переименовать через vistamp и записать в лог.
9. **git commit доски** — коммит-биография: счётчики переходов, ссылки UD-*/находки (N8, method §9).

## 11. vistamp (спека)

Node stdlib, без зависимостей. Запуск: `node <repo>/tools/vistamp/vistamp.mjs <verb> …`.

- `stamp --agent <имя> --card <NNN-slug|-> --kind <тип> [--dir <каталог>]` → печатает токен `YYYY-MM-DDTHHMMSSZ-<agent>-<card>-<kind>` (UTC, секунды). Файл записи = токен + `.md`; каталог вопроса = токен. Коллизия — следующий свободный момент в секундах (N10). Типы: `note, decision, question, blocked, review, done, q`.
- `id --slug <slug> [--board <путь>]` → `<NNN-slug>`: NNN = max по всем колонкам + 1 (pad до 3). Слаг `^[a-z0-9-]+$`.
- `find <id|фрагмент> [--board <путь>]` → абсолютные пути карточек, чьё имя содержит фрагмент — ре-резолв после mv (N6).

## 12. Экономия токенов (нормативная)

1. `ls` перед `read`: статус и таймлайн читаются листингом колонок и `board/log/`, без чтения содержимого.
2. Карточка читается точечно: README + нужные записи лога; не весь лог целиком без необходимости.
3. Записи 1–3 строки + указатель; «см. выше» запрещено — запись самодостаточна.
4. Промежуточная отчётность без потребителя не пишется; состояние — не append-only (история = git + записи логов).

## 13. Честные границы

1. Одна машина, один пользователь; распределённые сценарии вне периметра.
2. Git-история доски гранулярна до прохода менеджера: между проходами mv в истории не видны (N8); durability обеспечивается ФС и записями логов.
3. Лок — сигнал для честных агентов, не защита от злонамеренных (А7).
4. Возраст лока = время с его создания, ничем не продлевается — это и есть смысл порога 24ч (N5).
5. Знание текущего времени у LLM отсутствует: время — только через vistamp (А4).
6. Планирование запусков менеджера/агентов вне системы (UD-4); крон среды может дёргать сессии — протоколу безразлично.
7. Архивация done/ и project-log по месяцам — v2 (N13); сотни каталогов не блокер.
