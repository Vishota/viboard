# Журнал решений владельца — tasks (файловая доска)

Версия: 1.0 · Дата начала: 2026-11-20 · Метод: решения фиксируются **дословно (в кавычках)**, с датой и контекстом, хронологически. Идентификаторы UD-1, UD-2, … — для ссылок из канона, отчётов и коммитов. Идентификаторы не перенумеровываются никогда.

## История до репозитория (реконструкция одним блоком)

Дизайн системы разрабатывался в стороннем чате 2026-11-20. Полная реконструкция, критика и находки N1–N14 — [current/board-design-review.md](current/board-design-review.md). Принятая база (выдержала критику): четыре принципа — ФС = единственный источник правды; конвенции вместо замков; детерминистика в CLI, суждение в LLM; человек ставит задачи, менеджер роутит, агенты делают. Карточка = папка (`README.md` + `log/` + `assets/`), проектный лог массивом файлов, вопросы через `questions/` (отсутствующий `answer.md` = сигнал «открыт»), лок `mkdir .lock-<session>`, vistamp для детерминистики, stateless UI. Находки N1–N14 применены по правилу автономии (блок ниже), развилки В1–В4 — решениями владельца (UD-1…UD-4).

## 2026-11-20 · Пакет развилок В1–В4 (после разбора current/board-design-review.md)

**UD-1. Доска центральная (В1=А) (дословно):** «1 а».
Контекст: В1 = где физически живёт доска. Вариант А: доска в репо `tasks`, у карточки поле `project` во frontmatter; одна доска для UI и менеджера, кросс-проектная видимость; несовместимость с git worktrees код-репо устранена самой архитектурой.

**UD-2. review = верификация агентом-проверяющим (В2=А) (дословно):** «2 а».
Контекст: В2 = протокол колонки review/. Исполнитель двигает карточку в review/ с DoD-чеком; менеджер поручает проверку отдельному агенту-проверяющему (не исполнителю); вердикт в карточный log/; pass → done/, fail → возврат в doing/ с находкой. Продуктовые изменения — дополнительно владелец + прогон от лица пользователя (method §10).

**UD-3. Взятие задачи — гибрид (В3=А) (дословно):** «3 а».
Контекст: В3 = кто двигает todo→doing. Менеджер назначает assignee и диспетчеризует; агент при старте подтверждает клэйм `mkdir .lock-<session>`; самозахват из todo/ разрешён (проверка отсутствия assignee/лока + запись в карточный log/); нарушения менеджер ловит на проходе.

**UD-4. Менеджер запускается вручную; доска агент-агностична (В4=Б) (дословно):** «…с запуском чтобы возиться надо уже завязываться на конкретной агентной ide. да и в zcode есть свой cron. так что давай Б думаю»; «я думал сделать агент-агностичную доску — т.е. ею просто удобно пользоваться агентам и она направлена по дизайне на экономию токенов, но в целом по сути своей обычная доска».
Контекст: В4 = способ запуска менеджера. Проход менеджера — вручную, по поручению владельца, любой агентной сессией. Ядро протокола (аксиома А5) не зависит от агентной среды; планировщики запусков — вне системы.

## 2026-11-20 · Принято по правилу автономии (method §5; доклад в сессии 2026-11-20, возражений не поступило)

- **N1:** events.jsonl удалён из дизайна — дублирует состояние ФС (второй источник правды); валидатору хватает ls + mtime + git.
- **N5:** лок без heartbeat-touch (ритуал не выполнялся бы); устаревание = возраст mtime лока > 24ч ⇒ перехват с обязательной записью в карточный log/.
- **N6:** путь карточки никогда не кэшируется; ре-резолв по id через `vistamp find`.
- **N7:** README карточки разделён на зоны: frontmatter (меняется менеджером/владельцем) и тело-постановка (меняется только владельцем).
- **N8:** доску коммитит только менеджер на проходе (батч-коммиты-биографии); агенты доску не коммитят.
- **N10:** коллизия имён решается сдвигом на следующую свободную секунду — лексическая сортировка сохраняется.
- **N11:** имя агента — самодекларация для логов и диспетчеризации; session id — только для локов; реестра соответствий нет.
- Структура репо — по шаблону vishota/agents: spec.md (канон), decisions.md, agents.md, current/, archive/, templates/.
- Карточка — всегда папка; номер NNN сквозной по всей доске; WIP-лимиты — в `board/agents/<имя>.md`; .board.yml не вводится (мандат упрощения).

Контекст: реестр `board/agents/` (имена, capabilities, wip) унаследован из обсуждения в чужом чате и не был перепроверен под реальность zcode. **UD-6. Правила протокола — единым файлом agents.md (дословно):** «сами правила должны быть просто в agents.md - про порядок работы с lock, про роль менеджера, порядок работы с карточками и т.п.».
Контекст: протокол короткий; расщепление «канон (spec.md) + процесс (agents.md)» заставляло каждую сессию читать оба файла. agents.md v2.0 = протокол + процесс, единственный нормативный источник по доске; spec.md v0.1 и agents.md v1.0 — снапшоты в archive/. Осознанное отклонение от шаблона method §2: роль канона несёт agents.md.

**UD-7. vistamp может быть опубликован в npm как public (дословно):** «vistamp можно коммитить в npm как public если что».
Контекст: package.json готов к публикации (`private` убран); сама публикация и выбор лицензии — отдельные решения (open-questions №5; рекомендация: MIT).

**UD-8. Лицензия vistamp — copyleft GPL; repository-поле не ставится (дословно):** «ту лицензию, где сложнее копировать, но можно (с упоминанием итд), раз уж лицензируем»; про repository: «ну как бы этот же, просто он private.. ну либо прям на private, либо пустым оставляй, реши сам».
Контекст: владелец описал класс лицензии («сложнее копировать, но можно с условием»), конкретный выбор — по описанию. Интерпретация сессии: **GPL-3.0-only** (производные — только под той же лицензией; использование с сохранением уведомления об авторских правах и текста лицензии = «с упоминанием»). Альтернатива под то же описание — MPL-2.0 (поофайловый копyleft), выбрана более строгая. Файл `tools/vistamp/LICENSE` (канонический текст GNU GPL-3.0), в package.json — `"license": "GPL-3.0-only"`. Рекомендация MIT из UD-7 отклонена. Repository-URL: решение сессии по делегированию («реши сам») — поле `repository` **не ставить**: ссылка на private-репо в публичном пакете = мёртвая ссылка на странице npm; добавить, если репо станет публичным. Если под «сложнее копировать» имелось в виду иное (некоммерческое и т.п.) — заменить до публикации (одно поле + файл).

**UD-9. Репозиторий — шаблон; путь пользователя — `npx vitask`; владелец добавляет карточки через UI (дословно):** «вообще нам надо бы этот репо оставить как шаблон... как вообще юз кейс выглядит? как юзер получает эту доску? мб npx vitask? и оно сразу же пожнимает готовый ui и в нем же спрашивает, куда положить доску?.. а доска одна у юзера или одна на проект, хм. кому как удобнее?.. ну короче продумай пж как юзер будет пользоваться этим, чтобы было удобно»; «хотя вообще, дай мне просто ссылку на ui и я, как в реальности, сам первую добавлю».
Контекст: проработка юз-кейса делегирована сессии. Принятый юз-кейс:
- **vitask** — npm-пакет «консоль доски»: `npx vitask init` спрашивает, куда положить доску — **центральная на машину** (все проекты в одной доске, карточка несёт `project`; дефолт, у нас так по UD-1) или **в текущем проекте** (`./board`, изолированная); протоколу обе схемы безразличны (А5), выбор за пользователем в init. Скаффолдит структуру, кладёт протокол и шаблоны.
- `vitask ui` — поднимает локальный board-ui для доски (может зависеть от vistamp).
- **Доска одна или на проект — не дилемма протокола, а вопрос init'а**: обе схемы поддерживаются, «кому как удобнее» выбирает пользователь.
- Реестр проектов центральной доски: `board/projects.yml` (id → name, path) — §13.3.
- board-ui v0 реализован в этой сессии (tools/board-ui, §13.2) — владелец добавляет первую карточку сам через UI, «как в реальности».
- Реализация vitask — отдельная карточка на живой доске (после первого e2e-цикла); в канон несуществующее не пишется.
