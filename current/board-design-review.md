# Разбор дизайна «файловой доски для агентов» (обсуждение из стороннего чата)

Дата: 2026-11-20 · Статус: рабочий материал `current/`, до решений владельца.
Вход: расшифровка обсуждения из другого чата (передана владельцем) + методика `vishota/agents` (method.md, anti-patterns.md, templates/).
Задача: прогнать обсуждаемый дизайн заново, не принимая выводы чата за дефолт; найти проблемы; предложить решения.

---

## 1. Что в обсуждении утверждено (итог чата)

Четыре принципа, к которым чат «выкристаллизовался»:

1. ФС — единственный источник правды, всё остальное (UI, дайджесты) — одноразовые проекции.
2. Конвенции вместо принуждения, сигналы вместо замков (`.lock-<session>` = mkdir-атомарность).
3. Детерминистика — в крошечные CLI (vistamp: таймстампы, имена, id, коллизии), суждение — в LLM.
4. Человек пишет задачи (что/зачем), менеджер раскидывает (кому) и валидирует инварианты, агенты делают (как).

Анатомия из чата: `board/{backlog,todo,doing,blocked,review,done}`; карточка = папка `README.md + log/ + assets/ + .lock-<session>/`; проектный лог = массив файлов (не один растущий файл); вопросы владельцу = папка в `questions/` с отсутствующим `answer.md` как сигналом; `agents/` реестр; `events.jsonl` для «механики»; UI = stateless-проекция.

## 2. Вердикт: что выдерживает проверку

- Принципы 1–4 — да. Они согласуются с method.md (состояние вместо append-only, дешёвый шаг, «детерминистика в код» ≈ grep-гейты) и анти-паттернами (слоп рождается там, где LLM пишет текст; менеджер-роутер этого не делает).
- Карточка-папка с README.md как входной точкой — да (унифицированный примитив «сущность = папка», GitHub-рендер бонусом).
- Лок через `mkdir .lock-<session>` — да, атомарен и на POSIX, и на Windows; отсутствие read-check-write.
- Лог массивом файлов — да, с поправкой N10.
- `questions/` с отсутствующим answer.md как сигналом — да (третий повтор трюка «файл существует = событие»).
- vistamp и stateless UI — да.
- Отказ от inbox-транспорта (zcode умеет межсессионное общение) — да, подтверждается средой (в этой среде есть межсессионные инструменты).

## 3. Находки

Формат: `N# · серьёзность · суть → Суть → Предложение`. Это находки по обсуждаемому дизайну (канона проекта ещё нет — «Нарушает» даётся ссылкой на методику/анти-паттерны).

### N1 · высокий · events.jsonl — второй источник правды о состоянии доски

**Суть.** Состояние доски и так выражено ФС: позиция папки = статус, `.lock-*` = клэйм, mtime = время события, git = история. events.jsonl дублирует это и неизбежно разъедется (кто восстанавливает после сбоя? кто пишет при mv?). Чек-лист anti-patterns: «один и тот же факт обязан записываться больше чем в одно место» — прямое попадание. Писатели-агенты в один append-only файл — та же race-проблема, от которой чат ушёл в логах массивом файлов.

**Предложение.** Убрать events.jsonl полностью. Валидатору менеджера хватает `ls` + mtime + git log. Аудит-хвост, если когда-нибудь понадобится, пишется постфактум скриптом из ФС.

### N2 · высокий · не решено, где физически живёт доска

**Суть.** Чат отложил «отдельной темой» вопрос «если агенты разъедутся по git worktrees, доска должна остаться одна на всех». Но это определяет всё: пути UI, место проектного лога, работу менеджера, доступ агентов. Три варианта: (А) центральная доска в отдельном репозитории (карточка несёт поле `project`); (Б) доска внутри репо каждого проекта; (В) отдельный board-репо на каждый проект. Вариант Б несовместим с worktrees кода (доска расщепится по копиям репо).

**Предложение.** Вариант А: центральная доска в репо `tasks` (методология + инструменты + живая доска = собачья еда). Карточка: поле `project` во frontmatter. Плюсы: одна доска для UI и менеджера, кросс-проектная видимость, доска работает и для «проектов» без репо. Минусы: история доски живёт в одном репо с историей инструментов (не мешает — разные каталоги).

### N3 · высокий · колонка review/ без протокола

**Суть.** review/ есть в скелете, но протокола нет: кто проверяет, по какому критерию, кто двигает в done/, что происходит при отклонении. Единственное определённое требование — запись в проектный лог при переносе в done/. Анти-паттерн method.md §10: «код написал» ≠ «сделал».

**Предложение (рекомендуется, решает владелец — В2).** review/ = «на верификации»: исполнитель двигает карточку в review/ с DoD-чеклистом (проставленным в карточном log/); менеджер поручает проверку отдельному агенту-проверяющему (по формату находки vishota/agents: вердикт в карточный log/); проверяющий двигает в done/ или возвращает в doing/ с находкой. Продуктовые изменения (видимое пользователю) — дополнительно владелец + прогон от лица пользователя (method §10). Альтернативы в В2.

### N4 · средний · два механизма взятия задачи не стыкованы

**Суть.** Чат хочет диспетчера («раскидывать карточки по агентам») и одновременно спроектировал самозахват (mkdir-лок). Кто двигает todo→doing? Если оба — гонки между менеджером и агентом; если только менеджер — лок почти не нужен; если только агенты — диспетчеризация исчезает.

**Предложение (рекомендуется, решает владелец — В3).** Гибрид: менеджер назначает assignee и двигает в doing/ (диспетчеризация); агент при старте подтверждает клэйм `mkdir .lock-<session>` — лок существует как сигнальный примитив в обоих сценариях; самозахват из todo/ разрешён (агент проверяет отсутствие assignee/лока, после захвата — запись в карточный log/). Менеджер на проходе ловит нарушения (занято без лока, лок без assignee) — конвенции вместо замков.

### N5 · средний · heartbeat-touch на локе — ритуал, который не будет выполняться

**Суть.** Чат: «продление = touch .lock-*.» Живые сессии не делают touch по расписанию; требование периодического touch — дорогой шаг (anti-patterns #2), он будет молча игнорироваться, и разница «мёртвый лок» vs «живой без touch» исчезнет.

**Предложение.** Без heartbeat. Устаревание = возраст mtime лока > 24ч ⇒ карточку можно перехватить (с обязательной записью в карточный log/). Менеджер на проходе помечает зависшие карточки и создаёт вопрос владельцу, если висит долго. Порог щедрый, потому что реальный сценарий провала — «сессия умерла», а не «медленная работа».

### N6 · средний · путь карточки = статус ⇒ кэшированные пути ломаются

**Суть.** Папка переезжает между колонками ⇒ любой агент, держащий в контексте абсолютный путь, после чужого mv получит «файл не найден» и может создать карточку-двойник по старому пути.

**Предложение.** Конвенция: путь карточки никогда не кэшируется; ре-резолв по id (`rg --files | grep <id>` или `vistamp find <id>`). vistamp получает verb `find`.

### N7 · средний · «карточка неизменяема» противоречит assignee-обновлениям

**Суть.** Чат назвал README карточки «неизменяемым», но менеджер обязан писать туда assignee, а владелец — уточнять постановку. Формулировка порождает либо нарушения, либо паралич.

**Предложение.** Разделить README на зоны: frontmatter (меняется менеджером/владельцем: assignee, priority, depends_on) и тело-постановка (меняется только владельцем; агент и менеджер тело не переписывают никогда; уточнения — в карточный log/ или questions/). Запрет «менеджер не пишет body» сохраняется — это анти-слоп-инварианта чата.

### N8 · средний · параллельные сессии и git: кто коммитит доску

**Суть.** Несколько сессий-агентов в одном рабочем дереве доски: параллельные `git add/commit` дерутся за index.lock; незакоммиченные mv пропадают из истории. «Незакоммиченная работа — не работа» (anti-patterns #4) для доски надо исполнить без гонок.

**Предложение.** Доску коммитит только менеджер на проходе (батч-коммит «board pass: счётчики», стиль коммитов-биографий). Агенты доску не коммитят: их история — log/ файлы внутри карточек, durability — ФС одной машины. Отклонение от чата (там git mv как красивая история): история переходов остаётся видимой в batch-коммитах после факта.

### N9 · средний · стык канала вопросов с протоколом vishota/agents

**Суть.** Методика требует: вопросы владельцу — пакетами, самодостаточные, с рекомендацией, решения фиксируются дословно (UD). Дизайн чата добавляет questions/ как асинхронный канал. Без явных правил стыка получится два источника правды: часть решений в чате, часть в answer.md.

**Предложение.** Правило в канон: живая сессия спрашивает в чате (пакетно, по method §4) — но любой ответ, влияющий на карточку, обязан материализоваться: сессия пишет answer.md в вопрос-папку дословно (или запись type: decision в карточный log/). answer.md — слово владельца, не редактируется агентами. Асинхронный вопрос (сессия умирает / владелец не отвечает) — сразу в questions/.

### N10 · низкий · коллизия `--2` ломает лексическую сортировку лога

**Суть.** `…-done--2.md` сортируется раньше `…-done.md` (`-` < `.` в ASCII) ⇒ порядок событий нарушается ровно на коллизиях.

**Предложение.** vistamp при коллизии двигает время/добавляет нулевой суффикс внутри секунды (`T143201Z-…`), имена остаются лексикографически отсортированными. Деталь спеки vistamp.

### N11 · низкий · двойная идентичность: имя агента vs session id

**Суть.** Локи и клэймы — session id; реестр, логи, диспетчеризация — имя агента. Хранить соответствие бессмысленно (сессии эфемерны).

**Предложение.** Принять: имя — самодекларация агента для логов и диспетчеризации; session id — только для локов. Никакого реестра соответствий. Зафиксировать в каноне, чтобы не изобрели.

### N12 · низкий · фактические утверждения чата: проверка

kanban-md (antopolskiy/kanban-md) — реален, описание совпадает (frontmatter, статусы, claims, локальный бинарник). BMAD-METHOD, task-master — реальны. А вот «SE-Blackboard: 82.6% против 55.1% точности попадания в файл (arXiv 2510.01285)» — цифры к этой статье не относятся: 2510.01285 — «LLM-Based Multi-Agent Blackboard System for Information Discovery in Data Science», там 57% улучшения end-to-end success и 9% прироста точности в другой постановке. Направление («доска лучше пересказа») поддерживается литературой, конкретные цифры из чата не подтверждены — в канон их не включать.

### N13 · низкий · done/ и проектный лог растут бесконечно

**Предложение.** Архивация по месяцам (done/2026-11/…) — обязанность менеджера на проходе, v2. Не блокер: сотни каталогов ФС тянет.

### N14 · низкий · WIP-лимиты и классы обслуживания

**Предложение.** v1: WIP-лимиты в .board.yml, менеджер считает на проходе. Классы обслуживания (kanban-эзотерика) — не нужны. Мандат упрощения.

## 4. Решения, принятые автономно (в рамках методики)

- Структура репо — по шаблону vishota/agents: `agents.md` (процесс), `spec.md` (канон протокола доски), `decisions.md` (UD-журнал), `current/`, `archive/`, `templates/`. Единый CONVENTIONS.md из чата не создаётся (роли файлов method §2).
- Карточка — всегда папка с README.md (унификация примитива; вариант «файл до обрастания» из раннего чата отброшен).
- answer.md может писать живая сессия (дословная фиксация ответа владельца), UI — не единственный писатель.
- Менеджер не двигает карточку с живым .lock-* (гонка mv vs запись в лог).
- Менеджер работает на дешёвой модели (method §8.3); LLM-суждение нужно ему только в серых зонах роутинга.
- Слаги карточек — латиницей, lowercase; кириллица — в телах (Windows/UTF-8 ок).
